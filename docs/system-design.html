Omni system design

How Omni (assembly Omni.App) is built today: the Razor Pages dashboard, the .NET API and its workers, the WhatsApp/Telegram/calendar/knowledge integrations, the n8n workflows as seen from the app, and the PostgreSQL schema. Written from the code, not from older docs.

Last verified against code: 2026-10-26 Code baseline: bb95a8c on branch refactor/generic-platform (Milestone A) .NET 10 · EF Core / Npgsql · PostgreSQL + pgvector · SignalR

This is a living document. Any change that adds or alters a feature, endpoint, table, integration, background job, config key or n8n contract must update the matching section here in the same change, and add a line to the change log. The rule is also in CLAUDE.md at the repo root.

1. Overview

Omni is a multi-tenant SaaS for service businesses. A prospective customer (a contact) messages a client on WhatsApp or Telegram. An AI assistant, orchestrated in n8n, answers from the client's Knowledge Base, qualifies the contact and books, moves or cancels bookings through Omni's own tool endpoints. The client's people (client and member users) watch every conversation live in the Inbox and can take over at any moment. Clients also run WhatsApp template campaigns, mainly to reactivate old contacts.

Conversations

Unified Inbox for WhatsApp and Telegram, AI / human modes, take over and return to AI, unread tracking, WhatsApp 24-hour service window, template sends.

Contacts & booking

Contacts (the sidebar shows the client's own word for them), services catalog, structured availability, month calendar, AI booking tools with a per-client lock, orders.

WhatsApp business

Embedded Signup, message templates with Meta review status, account and phone health, campaigns with audience picker and reply/booking attribution.

Knowledge Base

Manual entries, PDF/DOCX/TXT upload, website crawling, chunking + embeddings, pgvector semantic search for the AI, retrieval benchmark.

Client admin

Self-service registration (one new client per signup), Google sign-in, client info and opening hours, members (the client user adds and deactivates them), notification bell, calendar and TikTok connections.

Billing

Subscription plans with entitlements and included credit; prepaid wallet; usage billed per billable event from versioned rate cards (reserve, settle, release); append-only financial ledger. Off until Billing:Enabled.

2. High-level design

2.1 System context

One ASP.NET Core process serves the dashboard (server-rendered Razor Pages plus small vanilla JS files), a JSON API, a SignalR hub and two in-process background workers. PostgreSQL (Supabase) is the single source of truth. n8n holds no business state: it runs the AI assistant and two helper workflows, and talks to the app only over HTTP.

2.2 Multi-tenancy

  • Tenant = client. Every business table carries client_id (FK to clients, on delete cascade), and every service method takes a clientId and filters on it.
  • Dashboard requests never trust a client id from the browser. ICurrentClientContext resolves it from the signed-in user's UserAccess (ClientRepository.GetUserAccessAsync, cached per user): an active client or member user (identity.users.role) with an active client_users row. One active membership per user is a rule in code (MemberService), not an index. The cookie is re-checked on every request (CurrentClientContext.ValidatePrincipalAsync, cookie OnValidatePrincipal): no access any more, or a security stamp that changed (password reset, lock), signs the user out at once.
  • Webhooks resolve the client from the stored connection: Meta events by phone_number_id then WABA id on channel_integrations; Telegram by the connectionId in the URL plus its secret token.
  • n8n tool calls pass clientId explicitly (query or body) and are trusted because of the shared X-Ingest-Key. This is the weakest link; see §10.
  • Registration always creates a brand-new, empty client of the business type the owner picks, plus its first user with role client and that user's client_users row in one transaction (ClientRegistrationService). The client user then invites member users by email on the Members page (they choose their own password from the link); members use everything else but can't manage members (D5). Seats: active client and member users count against the plan's max_users.
  • SignalR groups are client:{id} (joined on connect from the server-resolved client) and conversation:{id} (joined only after an ownership check).

2.4 Deployment and runtime

  • Multi-stage Dockerfile (SDK 10.0 build, aspnet 10.0 runtime). Listens on plain HTTP ${PORT:-8080}; Render terminates TLS. Deployed from main to https://sculptflowapp.onrender.com. No CI workflow files are in the repo.
  • UseForwardedHeaders trusts X-Forwarded-Proto so redirect URIs and secure cookies see https.
  • Swagger UI at /swagger in Development only. HSTS and /Error handler outside Development.
  • Schema is applied by hand: Database/schema.sql (idempotent, append-only blocks), then Database/seed-config.sql; seed.sql and seed-demo.sql are demo data for local databases only. The admin portal's Database/admin-schema.sql runs after the main app's schema. EF Core migrations are not used. Moving the old project into a new one and the order of every deploy step for both apps: docs/deploy-runbook.md.
  • The admin portal (Omni.Admin, own repo) is a second Render service on the same database; it signs admins in and does everything else through /api/platform-admin, so it needs MainApp:PublicBaseUrl (or ApiBaseUrl) and MainApp:PlatformAdminApiKey.
  • Secrets: dotnet user-secrets locally, Render env vars (Section__Key) in production. Properties/launchSettings.json on dev machines holds real keys and must never be committed.
  • Single instance assumed: the scrape and benchmark queues are in-memory Channel<Guid>s, recovered from DB state on startup. SignalR has no backplane. (Billing is the exception: its correctness rests on database row locks and unique keys, so two instances running the billing worker can't double-charge.)

2.5 Design principles visible in the code

  1. PostgreSQL is authoritative; SignalR only says "something changed". Every client handler re-fetches over REST.
  2. Business logic lives in Business/, shared by Razor PageModels and API controllers. Controllers and PageModels hold no logic; database access belongs in Persistence/ repositories (§4.1).
  3. The backend decides; the AI asks. Mode checks, slot validity, duplicate-booking guard and AI eligibility are decided in .NET, not in n8n.
  4. Idempotency at the database. Partial unique indexes on external ids (messages, contacts, Telegram threads, health events) make webhook retries safe.
  5. Side effects after commit, never throwing. Notifications, calendar sync and AI triggers run after the main write succeeds and swallow their own failures.
  6. Time: every instant is timestamptz (UTC). Activity shows in the viewer's timezone; bookings default to client time with a Client/My time switch; availability is entered and stored client-local.
  7. Tolerate provider vocabularies. Meta template and health statuses are free text (CHECK constraints dropped) so unknown values never fail a webhook.
  8. Money moves only through the ledger. Every balance change is an append-only ledger row written in the same transaction, under the client's billing-account row lock, with an idempotency key (§2.6).

2.6 Subscriptions and usage billing

An internal module (the Billing feature folders under Business/, Entities/ and Persistence/, tables in the Postgres schema billing.*, guide in docs/billing.md) built around three separate questions that are never collapsed into one:

  1. Platform subscription: what the client pays Omni for access. The plan decides features and limits (entitlements) and may grant a monetary included credit each period.
  2. Provider billing responsibility: who pays the upstream provider (Meta, an SMS operator…), set per connected channel account: customer pays directly, Omni pays, customer pays an external provider, or no provider usage fee. Two WhatsApp accounts can differ.
  3. Omni usage billing: whether Omni charges the client for the usage. By default only when Omni pays the provider; an account can also carry an Omni usage fee, or Omni can absorb the cost.

Every usage is a billable event and is recorded (volumes, provider cost where known). Only what Omni charges is rated, reserved, settled and paid, included credit first and then the prepaid wallet, through the ledger. There are no per-channel quotas. Everything is off while the Billing / Enabled setting is false (on by default; switch it on the admin portal's Configuration page).

  • Billable event, not message. A typed event (whatsapp_marketing_message, telegram_message, ai_reply, later sms_segment, voice_minute, ai_token…) with a quantity, plus who pays the provider and whether Omni charges. New types need only rates, and only where Omni charges.
  • AI replies are usage too. Each AI assistant reply reserves one ai_reply (key ai:reply:{messageId}, channel ai, built-in platform_funded) before it is sent and settles when the provider accepts it, on top of the channel's own message usage, so it is paid from included credit and then the wallet. No rate or not enough balance: the reply isn't sent, the refusal is a failed usage row and the conversation goes to the team (ConversationService.HandOverUnpaidAiReplyAsync). Billing:ChargeAiReplies switches it off.
  • Channel policies own channel rules (IChannelBillingPolicy: which event, how many units, when it counts); accounts own commercial arrangements (ProviderBillingService: account override → configured default per channel/provider → built-in default).
  • Usage records keep money and provider apart: charge_status (reserved, settled, released, failed, not_charged) is Omni's money; provider_outcome (pending, billable, not_billable) is what happened at the provider.
  • Rates hold provider cost and client rate as independent numbers, optionally narrowed by country, operator, provider and responsibility, versioned by effective period; never edited, never backdated, so history is never re-priced. A customer-paid account is only ever charged a rate set for its own responsibility (a usage fee), never the platform rate by fallback.
  • Prepaid. Spendable = wallet + included credit − reserved. The wallet and credit only finance what the client owes Omni. Only a settlement that costs more than its estimate can take the wallet below zero.
  • Correctness. Every money operation runs in one transaction holding the client's billing.accounts row lock, checks idempotency after taking the lock, and writes the ledger; unique keys, CHECKs, an exclusion constraint on rate versions and triggers that block ledger/rate/final-usage edits back it up. Cached balances must equal the ledger sums (reconciliation endpoint).
  • Postpaid later fits as a credit limit on the billing account (added to the spendable formula) plus invoices built from the ledger; nothing else has to change.

3. Frontend

Server-rendered ASP.NET Core Razor Pages with two layouts (Pages/Shared/_Layout.cshtml for signed-in client and member users, _AuthLayout.cshtml for sign-in and error pages), the vendored "Aurora" UI kit plus an app stylesheet, and one small vanilla JS file per interactive page. There is no bundler, no npm and no frontend framework. Razor runtime compilation is off, so .cshtml changes need a rebuild. How screens look is governed by docs/UI_GUIDE.md (§0.4 = how this app applies it).

3.3 CSS, theming and time display

  • Styles load as fonts.css → aurora.css → site.css. aurora.css / aurora.js are the vendored Aurora kit, shared with the admin portal and extracted from docs/UI_GUIDE.md's appendices (never edited by hand). site.css is the app layer: older token and class names mapped onto the kit's tokens (the page scripts still build markup with them), the brand calibration (teal, calm, AA) and per-screen styles.
  • Fonts are self-hosted in wwwroot/fonts: Inter, Noto Sans Arabic (Arabic letters only, through unicode-range, so it loads only on pages that show Arabic) and a Material Symbols subset holding only the icons in use, rebuilt with node docs/tools/icon-font.js after adding an icon.
  • Right to left: Arabic pages render as <html lang="ar" dir="rtl">. aurora.css and site.css use logical properties only (margin-inline-start, inset-inline-end, text-align: start…), so the same rules mirror; --au-x (1, or -1 under [dir='rtl']) flips horizontal translateX moves and the sidebar gradient. Directional icons carry au-icon--dir (list in Common/Helpers/IconDirection); phones, emails, URLs and codes are dir="ltr", user content dir="auto". Guards/RtlStyleTests fails on physical left/right in CSS, inline styles or scripts and on an unmirrored directional icon. Rules: docs/UI_GUIDE.md §0.4.
  • Light and dark: the theme follows the OS until the user picks one; the choice is stored in localStorage['client.themeMode'] and applied as <html data-theme> by _ThemeScript before the first paint. The collapsed sidebar rail is localStorage['client.sidebarCollapsed'] (<html class="au-side-collapsed">). The old sf-theme / sf-sidebar keys are read once as a fallback.
  • Brand: wwwroot/logo.svg (also the favicon), teal (<html data-brand="teal">), dark sidebar. User-visible name is Omni.
  • Time rule: UTC in the DB; activity in viewer time; bookings in client time with a switch; availability client-local. Server-side day boundaries use the omni-tz cookie via ViewerTimeZone.

5. Key flows (low-level)

5.1 Inbound WhatsApp message to AI reply

  1. Meta posts raw JSON to POST /api/integrations/whatsapp/webhook.
  2. MetaWebhookParser splits it into ParsedMetaEvents (customer message, business-app echo, status, template, health, history, app-state, unknown). Interactive/button replies become clean text plus SelectedValue.
  3. MetaWebhookProcessor resolves the client per event from channel_integrations (phone_number_id, else WABA id) and dispatches to the handler.
  4. CustomerMessageHandler → ContactService.GetOrCreateByPhoneAsync → conversation get-or-create → MessageService.IngestAsync: idempotent on (client, channel, external_message_id), stores the message, opens the 24h window, unread, campaign reply attribution, events, notifications, NewMessage.
  5. The conversation's mode decides who answers: a new conversation starts in human unless the WhatsApp account's bot answers new conversations; a customer message in an AI conversation moves it to human when no bot answers the account any more, or when it reopened the conversation and the account sends reopened conversations to the team. See InboxSettingsService.ResolveAsync.
  6. If the event is AI-eligible (customer message, conversation mode ai, not a duplicate) the controller calls AiTriggerNotifier, which adds the account's bot (IBotRuntimeService.ConfigAsync) and the client's profile and posts to N8n:AiWebhookUrl (§7.1). Never throws.
  7. Meta always gets HTTP 200.
  8. n8n AI workflow runs that bot: it calls the /api/ai/* tools Omni lets it use ([BotTool]), then POST /api/ai/conversations/{id}/reply?clientId= (or handoff).
  9. MessageService.SendAiReplyAsync re-reads the mode; if a human took over it returns 409 and nothing is sent. Otherwise WhatsAppChannelSender sends through the Graph API and the message is stored with origin=ai.

5.2 Member reply, echo and status

  • Member reply from the Inbox: POST …/messages/send (session) → MessageService.SendAsync → channel sender (throws before persisting if it cannot send; WhatsApp requires an open 24h window) → store origin=dashboard → mode flips to human.
  • Closed window: 409; the Inbox offers send-template with an approved template.
  • Coexistence echo: a reply typed in the WhatsApp Business phone app arrives as a BusinessAppEcho, is stored with origin=whatsapp_business_app, flips the conversation to human, and never triggers AI.
  • Delivery status: MessageStatusHandler updates delivery_status and the matching delivered_at/read_at/failed_at, mirrors campaign recipient status, raises OUTBOUND_MESSAGE_FAILED on failure, broadcasts MessageStatusUpdated.

5.3 Conversation modes

mode ∈ {ai, human, approval}. Switches to human: a member's Take Over, a member's message or template, a business-app echo, the AI's handoff_to_human, a campaign template send, a customer message when no bot answers the conversation's account (plan without ai_assistant, AI off, no bot, an inactive bot, a bot beyond max_ai_bots), a contact reopening a conversation when the account's reopened switch is off, billing refusing an AI reply's ai_reply (no rate or no balance). A new conversation starts in human unless the account's bot answers new conversations. Only Return to AI switches back (refused without ai_assistant or an answering bot; the Inbox hides the button without the plan). approval exists in the schema but is never set automatically.

5.4 Telegram

  2. Telegram posts an update; the controller checks the row is telegram + connected (else 404) and the secret header (else 403).

5.5 Booking (AI and dashboard)

  1. get_available_slots → AvailabilityService.GetSlotsAsync builds slots in the client's timezone and returns the contact's booking context.
  2. schedule_booking → BookingService.ScheduleAsync: no upcoming booking → book; one upcoming and ConfirmReplaceExisting → reschedule; otherwise CONFIRMATION_REQUIRED.
  3. Every mutation takes pg_advisory_xact_lock(hashtext(clientId)), re-runs CheckSlotAsync (excluding the booking being moved) and the one-upcoming-per-contact guard.
  4. After commit: event row, BOOKING_* notification, BookingChanged, and CalendarIntegrationService.TriggerBookingSyncAsync.

5.6 Campaigns

  1. Create (/Campaigns/Create): pick an approved template, fill variables, choose audience all_eligible | reactivation_no_booking | custom (filters JSON or manual selection). Recipients are snapshotted; non-reachable contacts are skipped with a reason.
  2. Send: POST /api/campaigns/{id}/send moves to running, queues pending recipients and processes the first batch (20); CampaignSenderWorker sends the rest (process-batch still works by hand). A scheduled campaign is started by the worker once scheduled_at passes.
  3. Stop: POST /api/campaigns/{id}/stop (Details page "Stop campaign") moves a scheduled or running campaign to paused, shown as "Stopped", with a conditional set-based update. Nothing more is sent, including the rest of a batch in progress; waiting recipients stay pending/queued. "Resume sending" is send again (keeps the first started_at); Cancel ends it. A campaign stopped or cancelled during its last batch is never marked completed.
  4. Each recipient: conversation get-or-create → MessageService.SendCampaignTemplateAsync (origin=campaign, links campaign ids) → mode flips to human.
  5. Attribution: status webhooks move recipients through sent → delivered → read; the first inbound reply after sent_at sets replied_at and CAMPAIGN_REPLY; bookings set booked_at/booking_id.

5.7 Calendar sync (one way, Omni → Google/Outlook)

  1. Connect: /calendar-oauth/{provider}/connect marks the row pending and redirects to consent; /callback exchanges the code, stores access/refresh tokens on calendar_integrations, lists calendars into calendar_integration_calendars.
  2. A member selects a calendar and enables sync.
  3. On every committed booking change, the service refreshes the token if needed, upserts booking_calendar_syncs (one row per booking × integration, new last_request_id, last_operation) and posts CalendarSyncTriggerPayload to N8n:CalendarSyncWebhookUrl (access token, calendar id, operation create/update/cancel, request id, external event id, start/end with offset, client timezone).

5.8 Knowledge Base ingestion and search

  • Manual / upload: text (or extracted text, max 5 MB file, 250k chars) → chunk by the client's settings (tokens ≈ chars ÷ 4) → embed all chunks first → transaction replaces knowledge_chunks for that document.
  • Website: create source → pending run enqueued → worker crawls breadth-first (robots.txt, SSRF-checked fetch, same-site links, max pages/depth/concurrency from Knowledge:WebScraping) → analyze (canonicals, boilerplate stripping by block hash, SHA-256 of normalized text, duplicates) → apply (unchanged pages skip embedding, changed pages rebuild only their chunks, new pages create source_type='website' documents, missing pages deactivate after confirmed absence).
  • Search: embed the query with the client's model, exact cosine scan over the client's active documents' chunks, take top-K, drop anything under minimum_similarity. No ANN index on purpose.

5.9 Retrieval benchmark

  1. Driven from the admin portal (Search benchmark page, client picked in its header) through /api/platform-admin/knowledge-benchmark/clients/{clientId}; client and member users have no benchmark page or API. Generate: the app creates a pending generation row, samples 20 active chunks and posts them with the generationId to N8n:KnowledgeBenchmarkWebhookUrl; returns 202.
  2. n8n's LLM writes one question per chunk and calls back POST /api/knowledge/benchmark/generations/{id}/questions. Every id is validated against the chunks that generation sent; the client comes from the generation row. Cancelled generations refuse late callbacks.
  3. Run: a pending run is queued; the worker searches each non-stale case via SearchRankedAsync and records chunk/document ranks, Top-1/3/5, MRR, latency and a settings snapshot.

5.10 Sign up and sign in

  • Register: full name, client name, email, business type (required picker of the active types), password → new client (unique slug) + user + membership in one transaction → signed in → /dashboard. With Accounts:SignupEnabled off, Register shows "sign-ups are closed" instead of the form, Login hides its "Create a client account" link, a new Google identity is sent back to Login (externalError=signup_closed), and both register methods refuse before creating anything.
  • Google: /auth/google/start → Google → /auth/google/callback: existing linked login or verified matching email signs in; a new email goes to /Account/CompleteGoogleSignup to collect the client name and business type. Errors return to Login with externalError=cancelled|failed.
  • Invites: the client user invites by email on /Members (a seat must be free; open invites hold one). The link /Account/AcceptInvite?token=… shows the client and email; the invitee types a name and password and is signed in as a member of that client (email confirmed). A used, cancelled or expired link says so; resending replaces the link; an email that already signs in is refused, before and at accept time.
  • Forgot password: /Account/ForgotPassword takes an email and always answers "if an account uses it, we sent a link". For an active client or member user under the hourly limit a token is stored (hash only) and the link /Account/ResetPassword?token=… is emailed. That page checks the link (open, not used, not revoked, user still active); saving validates the password rules first, then sets it, clears the lockout, confirms the email, renews the security stamp and closes the link and every other open reset link in one transaction, and sends the person to Login with "password changed".
  • Sign-in rules: only active client / member users with an active membership get in (AppSignInManager); anyone else sees the wrong-password text. Every request re-checks the cookie (§2.2).
  • Admin portal: the portal posts the admin's email and password to POST /api/platform-admin/auth/login, issues its own omni.admin cookie, and re-checks GET /api/platform-admin/auth/admins/{id} on every request (a "yes" kept one minute); a deactivated or demoted admin is signed out on the next click. Admins never sign in to this app.

5.11 Billing an outbound WhatsApp template (usage)

  1. MessageService (Inbox template, campaign recipient, or a billed free-form message) checks the subscription (EnsureCanSendMessages; expired/cancelled/no plan → 422) and generates the message id it will save.
  2. WhatsAppBillingPolicy describes the message: template category → whatsapp_{category}_message (utility inside an open 24h window and free-form replies are free by default), quantity 1, destination country from the contact's number, provider meta, settle on delivery.
  3. ProviderBillingService resolves the client's WhatsApp account: who pays the provider (account override, else the default — platform_funded for WhatsApp) and whether Omni charges usage.
  4. Omni doesn't charge (customer pays Meta directly, external provider, no fee): BillingService.Reserve only records the usage as not_charged, with Meta's cost if a rate knows it. No rate is required, nothing is held, the send goes ahead even with an empty wallet, and the outcome steps below only update provider_outcome.
  5. Omni charges: BillingService.Reserve (own transaction, client account locked) rates it (client card → plan card → default, rate effective now, most specific country/operator/provider/arrangement; a customer-paid account only matches a fee rate for its own arrangement), refuses if no rate or spendable < price (recorded as a failed usage row; the send is refused with 422 before the provider is called), else holds it and inserts the usage record keyed whatsapp:message:{messageId}.
  6. The provider call runs. If it throws, the hold is released (send_failed) and the error goes back as before.
  7. The message row is saved with the same id. Later, the provider's status callback reaches MessageService.HandleStatusUpdateAsync → MessageBillingService: delivered/read → settle (release the hold, charge included credit first, then wallet, one ledger row per balance), failed → release. Repeated or out-of-order callbacks are no-ops; settle-after-release is refused and logged.
  8. If no outcome arrives within Billing:ReservationTimeoutHours, the maintenance worker settles it when the message row shows it was delivered (callback processed but billing failed) and releases it otherwise.

5.12 Subscription start, renewal and expiry

  1. Start / change plan (admin API, or the signup plan): wallet must cover the price while keeping existing holds covered (unless the first period is waived); old included credit expires, the plan's credit is granted, the price is charged (a 0 charge row for free/trial periods), the period runs from now. Same idempotency key → no second charge.
  2. Renewal (worker, when current_period_end has passed): same steps for the next contiguous period. If the wallet can't pay: past_due, the ended period's credit expires, the plan keeps working for Billing:GracePeriodDays; every worker run retries, so a top-up renews it (from the old period end).
  3. Expiry: grace over without payment → expired. Cancel: now, or at period end instead of renewing → cancelled. Expired/cancelled clients can sign in and see everything, but can't send, run campaigns, use the AI or connect channels until a plan is started again.

5.13 Opt-out (stop words)

  1. Inbound: MessageService.IngestAsync checks a customer text or command (Telegram /stop) against the stop/start words (OptOut:Enabled). A match updates the contact in the same save (event logged), the AI is not asked (trace bot.skipped, reason opt_out_keyword), and one confirmation goes back through SendSystemTextAsync (sender and origin system, metadata {"automatic":true} so the Inbox shows a bubble rather than a marker; billed like any text; never changes the mode). A failed confirmation is traced, never fails the inbound message.
  2. What it blocks: Inbox templates and campaign sends to an opted-out contact are refused (inbox.errors.contactOptedOut, 422; a campaign recipient fails with that reason); campaign audiences already skip them; booking reminders skip them (S5). Member replies in a conversation the contact opens again are allowed.
  3. Contact page: an "Opted out" chip and a "Messages from you" note with Opt out / Opt back in (any member; opting back in asks for confirmation).

5.14 Auto-respond (automatic replies)

  1. When: MessageService.IngestAsync, after saving a genuine customer message (never an echo or an AI message): the contact's first message in the conversation (last_customer_message_at was empty, also when a campaign or reminder started it) uses the channel's new-conversation reply; a message that reopened a closed conversation uses the reopened reply (same = the new-conversation text). A stop/start word gets only its opt-out confirmation.
  2. AI bot (default): when the message goes to the AI bot (it is AI-eligible after the account's routing), nothing is sent unless the channel has send_when_ai_answers, so the contact doesn't get two replies. In human mode (no bot answers the account, reopened to the team) or for a message type the bot doesn't see, the reply goes out.
  3. Send: through the same path as the opt-out confirmation (sender and origin system, metadata {"automatic":true}, billed like any text, never changes the mode), event auto_reply_sent with {"trigger":"new"|"reopened"}. A reply held back (AI bot, AutoReply:Enabled off) is traced as inbox.auto_reply_skipped; a failed one as send.blocked (kind auto_reply); neither fails the inbound message.

5.15 AI bots: configure, assign, run, hand off, test

  1. Configure (Bots): a bot is a template (support, booking, sales: locked instructions and actions in BotTemplates) or custom (its own instructions and capabilities). Name, description, Knowledge Base scope, reply language and handoff settings are always the client's. Only an active bot answers; activating needs ai_assistant, instructions (and a source when "selected") and room under max_ai_bots (with add-ons). After a downgrade the newest active bots beyond the limit answer nobody (ai_bot_limit).
  2. Assign (Inbox settings): per connected account: AI on/off, one active bot, new / reopened switches. Off, no bot or an inactive bot = the team answers. The model, temperature and tokens are never exposed; usage is the ai_reply charge.
  3. Run: the trigger carries bot (§7.1); n8n's generic prompt wraps bot.instructions; every tool call sends X-Omni-Bot-Id and Omni refuses anything the bot isn't allowed (TOOL_NOT_ALLOWED), searches only its sources, and checks the bot is the client's own.
  4. Hand off: policy on_request (only when the contact asks for a person) or on_request_or_unsure (default; also when the bot can't confidently help); an explicit request is always honoured. handoff_to_human locks the conversation row: only a real ai → human change logs human_handoff, notifies, moves the contact to needs-human and sends the bot's handoff message (once; never for a member's take-over or a billing hand-over; skipped outside WhatsApp's window).
  5. Test: the editor's panel runs the same workflow with testSessionId (its conversationId and contactId are the session id): real instructions, Knowledge Base and allowed tools; replies charged as ai_reply; bookings, contact changes and handoff simulated on the session (§4.2 BotTestService); nothing reaches a provider.

8. Database

8.1 Conventions

  • One Postgres schema per area (since 2026-10-07): core (clients, services), identity (users with roles, ASP.NET Identity claims/logins/tokens, client_users), crm (contacts, orders, conversations, messages), scheduling (bookings, availability, calendar sync), channels (channel integrations, WhatsApp templates and health, TikTok), marketing (campaigns), knowledge (knowledge base, scraping, benchmarks), activity (events, notifications), billing, config; the admin portal's own tables are in admin. public keeps only set_updated_at() and extensions. SQL always schema-qualifies table names and every ToTable names its schema. The top of schema.sql creates the schemas and moves any table still in public (databases created before the split) with alter table … set schema, which keeps data, indexes, constraints, triggers and foreign keys; on a current database it does nothing. Supabase's Data API only exposes public, so no app table is reachable through it.
  • Database/schema.sql is the source of truth: idempotent, append-only blocks (create … if not exists, add column if not exists, guarded do $$ constraint blocks). New changes are appended at the end, never edited in place. ApplicationDbContext is updated by hand to match.
  • Keys: uuid with gen_random_uuid(), except Identity (text ids) and knowledge_retrieval_benchmark_generations.id (app-assigned).
  • created_at/updated_at on most tables; set_updated_at() trigger maintains updated_at.
  • All instants are timestamptz; a guard block at the end converts any stray timestamp column. Only availability time/date columns are zone-less (client-local).
  • Status columns are varchar with CHECK constraints, except deliberately free-text provider vocabularies (template status/category, health fields, campaign_type, contacts.source, knowledge_documents.category).
  • Tenant FK client_id … on delete cascade everywhere. Tokens (access_token, refresh_token) are plain text today.

8.5 Moving the old project's data (one-off)

Database/migrations/2026-10-generic/copy-from-old.sql copies the previous project's data into a new Omni project that already ran schema.sql and seed-config.sql (not the demo seeds). Run it once with psql against the new database; the old host and password are psql variables typed on the command line (-v old_host=… -v old_password=…), never stored in the file. It runs in one transaction: a postgres_fdw server and user mapping to the old project, each old schema imported as old_<schema>, checks (every old status exists as a stage of the first business type, no admin email equals a client user name), a refusal when any target table already has rows (-v force=1 empties them first), one insert … select per table in foreign-key order, identity columns moved past the copied ids, and a row-count report (old vs new per table) that ends in ok; a mismatch or any error rolls everything back, and the link to the old project (with its password) is dropped before the commit.

  • Mappings: every clinic_id / lead_id / procedure_id / appointment_id column and the renamed tables (§8.3); clients get business type clinic and language en; lead status becomes stage_key (same values) and qualification_status becomes qualification, where medical_question becomes needs_human and, for a contact in an open stage, the stage medical_question; order status booked → confirmed; booking type consultation → standard; message senders lead/staff → contact/member; event types, notification types and links, campaign audience_type and filter keys, knowledge categories, entitlement keys, usage rate_source, a trace step and error-log categories as in the rename map; settings changed by hand (updated_by not seed) under their new keys (unchanged defaults stay as the new seed wrote them; vanished keys are listed and skipped). Business types, stages and AI profiles are not copied (they come from schema.sql).
  • Users: identity.identity_users → identity.users; the earliest membership of each client is its owner (role client), everyone else is a member (the report lists them to check); the full_name claim becomes users.full_name. admin.admin_users become users with role admin (same id as text, same password hash, new security stamp, lockout and active flag kept) and admin.admin_audit_log is copied with user_id (text) and client_id; the script creates that table in its final shape if it is missing.
  • Test: test-copy.ps1 (same folder) builds a throwaway cluster, loads the old project from git (main schema, old seeds, the portal's admin-schema.sql, test-old-extras.sql) and a new one from this branch, runs the script, runs test-copy-assert.sql (row counts, each mapping, users, admins, settings, sequences), checks the refusal / force / no-trace-after-failure behaviour, then publishes the app and signs in a migrated client user, a member and a migrated admin (platform-admin login). Guards/CopyScriptCoverageTests (in dotnet test) fails when schema.sql gains or loses a table the script does not follow. Any later schema.sql change to a copied table must update the script, the assertions and the extras.
  • Order: new project: schema.sql, seed-config.sql, this copy, then the portal's admin-schema.sql (a no-op there, since the copy already made admin.admin_audit_log in its final shape). The portal's admin-schema.sql must never run on the old project: the old portal and this copy both read its old columns. Full step list for both apps: docs/deploy-runbook.md.
