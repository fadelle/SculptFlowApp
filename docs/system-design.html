SculptFlow system design

How SculptFlow (repo name MySculptFlow, assembly PlasticSurgery) is built today: the Razor Pages dashboard, the .NET API and its workers, the WhatsApp/Telegram/calendar/knowledge integrations, the n8n workflows as seen from the app, and the PostgreSQL schema. Written from the code, not from older docs.

Last verified against code: 2026-10-09 Code baseline: 12fad04 (main) + branch feature/subscription-billing .NET 10 · EF Core / Npgsql · PostgreSQL + pgvector · SignalR

This is a living document. Any change that adds or alters a feature, endpoint, table, integration, background job, config key or n8n contract must update the matching section here in the same change, and add a line to the change log. The rule is also in CLAUDE.md at the repo root.

1. Overview

SculptFlow is a multi-tenant SaaS for plastic surgery clinics. A prospective patient (a lead) messages a clinic on WhatsApp or Telegram. An AI agent, orchestrated in n8n, answers from the clinic's Knowledge Base, qualifies the lead and books, moves or cancels consultations through SculptFlow's own tool endpoints. Staff watch every conversation live in the Inbox and can take over at any moment. Clinics also run WhatsApp template campaigns, mainly to reactivate old leads.

Conversations

Unified Inbox for WhatsApp and Telegram, AI / human modes, take over and return to AI, unread tracking, WhatsApp 24-hour service window, template sends.

Leads & booking

Leads ("Interested People"), procedures catalog, structured availability, month calendar, AI booking tools with a per-clinic lock, procedure bookings.

WhatsApp business

Embedded Signup, message templates with Meta review status, account and phone health, campaigns with audience picker and reply/booking attribution.

Knowledge Base

Manual entries, PDF/DOCX/TXT upload, website crawling, chunking + embeddings, pgvector semantic search for the AI, retrieval benchmark.

Clinic admin

Self-service registration (one new clinic per signup), Google sign-in, clinic info and opening hours, staff list, notification bell, calendar and TikTok connections.

Billing

Subscription plans with entitlements and included credit; prepaid wallet; usage billed per billable event from versioned rate cards (reserve, settle, release); append-only financial ledger. Off until Billing:Enabled.

2. High-level design

2.1 System context

One ASP.NET Core process serves the dashboard (server-rendered Razor Pages plus small vanilla JS files), a JSON API, a SignalR hub and two in-process background workers. PostgreSQL (Supabase) is the single source of truth. n8n holds no business state: it runs the AI agent and two helper workflows, and talks to the app only over HTTP.

2.2 Multi-tenancy

  • Tenant = clinic. Every business table carries clinic_id (FK to clinics, on delete cascade), and every service method takes a clinicId and filters on it.
  • Dashboard requests never trust a clinic id from the browser. ICurrentClinicContext resolves it from the signed-in Identity user through clinic_users (one active membership per user, enforced by the partial unique index ux_clinic_users_user_active).
  • Webhooks resolve the clinic from the stored connection: Meta events by phone_number_id then WABA id on channel_integrations; Telegram by the connectionId in the URL plus its secret token.
  • n8n tool calls pass clinicId explicitly (query or body) and are trusted because of the shared X-Ingest-Key. This is the weakest link; see §10.
  • Registration always creates a brand-new, empty clinic plus its first clinic_users row in one transaction (ClinicRegistrationService). There is no invite or join flow yet, and no roles: every member of a clinic has full access.
  • SignalR groups are clinic:{id} (joined on connect from the server-resolved clinic) and conversation:{id} (joined only after an ownership check).

2.4 Deployment and runtime

  • Multi-stage Dockerfile (SDK 10.0 build, aspnet 10.0 runtime). Listens on plain HTTP ${PORT:-8080}; Render terminates TLS. Deployed from main to https://sculptflowapp.onrender.com. No CI workflow files are in the repo.
  • UseForwardedHeaders trusts X-Forwarded-Proto so redirect URIs and secure cookies see https.
  • Swagger UI at /swagger in Development only. HSTS and /Error handler outside Development.
  • Schema is applied by hand: psql -f Database/schema.sql (idempotent, append-only blocks), optional Database/seed.sql. EF Core migrations are not used.
  • Secrets: dotnet user-secrets locally, Render env vars (Section__Key) in production. Properties/launchSettings.json on dev machines holds real keys and must never be committed.
  • Single instance assumed: the scrape and benchmark queues are in-memory Channel<Guid>s, recovered from DB state on startup. SignalR has no backplane. (Billing is the exception: its correctness rests on database row locks and unique keys, so two instances running the billing worker can't double-charge.)

2.5 Design principles visible in the code

  1. PostgreSQL is authoritative; SignalR only says "something changed". Every client handler re-fetches over REST.
  2. Business logic lives in Business/, shared by Razor PageModels and API controllers. Controllers and PageModels hold no logic; database access belongs in Persistence/ repositories (§4.1).
  3. The backend decides; the AI asks. Mode checks, slot validity, duplicate-booking guard and AI eligibility are decided in .NET, not in n8n.
  4. Idempotency at the database. Partial unique indexes on external ids (messages, leads, Telegram threads, health events) make webhook retries safe.
  5. Side effects after commit, never throwing. Notifications, calendar sync and AI triggers run after the main write succeeds and swallow their own failures.
  6. Time: every instant is timestamptz (UTC). Activity shows in the viewer's timezone; appointments default to clinic time with a Clinic/My time switch; availability is entered and stored clinic-local.
  7. Tolerate provider vocabularies. Meta template and health statuses are free text (CHECK constraints dropped) so unknown values never fail a webhook.
  8. Money moves only through the ledger. Every balance change is an append-only ledger row written in the same transaction, under the clinic's billing-account row lock, with an idempotency key (§2.6).

2.6 Subscriptions and usage billing

An internal module (the Billing feature folders under Business/, Entities/ and Persistence/, tables in the Postgres schema billing.*, guide in docs/billing.md) built around three separate questions that are never collapsed into one:

  1. Platform subscription: what the clinic pays SculptFlow for access. The plan decides features and limits (entitlements) and may grant a monetary included credit each period.
  2. Provider billing responsibility: who pays the upstream provider (Meta, an SMS operator…), set per connected channel account: customer pays directly, SculptFlow pays, customer pays an external provider, or no provider usage fee. Two WhatsApp accounts can differ.
  3. SculptFlow usage billing: whether SculptFlow charges the clinic for the usage. By default only when SculptFlow pays the provider; an account can also carry a SculptFlow usage fee, or SculptFlow can absorb the cost.

Every usage is a billable event and is recorded (volumes, provider cost where known). Only what SculptFlow charges is rated, reserved, settled and paid, included credit first and then the prepaid wallet, through the ledger. There are no per-channel quotas. Everything is off while the Billing / Enabled setting is false (on by default; switch it on the admin portal's Configuration page).

  • Billable event, not message. A typed event (whatsapp_marketing_message, telegram_message, later sms_segment, voice_minute, ai_token…) with a quantity, plus who pays the provider and whether SculptFlow charges. New types need only rates, and only where SculptFlow charges.
  • Channel policies own channel rules (IChannelBillingPolicy: which event, how many units, when it counts); accounts own commercial arrangements (ProviderBillingService: account override → configured default per channel/provider → built-in default).
  • Usage records keep money and provider apart: charge_status (reserved, settled, released, failed, not_charged) is SculptFlow's money; provider_outcome (pending, billable, not_billable) is what happened at the provider.
  • Rates hold provider cost and client rate as independent numbers, optionally narrowed by country, operator, provider and responsibility, versioned by effective period; never edited, never backdated, so history is never re-priced. A customer-paid account is only ever charged a rate set for its own responsibility (a usage fee), never the platform rate by fallback.
  • Prepaid. Spendable = wallet + included credit − reserved. The wallet and credit only finance what the clinic owes SculptFlow. Only a settlement that costs more than its estimate can take the wallet below zero.
  • Correctness. Every money operation runs in one transaction holding the clinic's billing.accounts row lock, checks idempotency after taking the lock, and writes the ledger; unique keys, CHECKs, an exclusion constraint on rate versions and triggers that block ledger/rate/final-usage edits back it up. Cached balances must equal the ledger sums (reconciliation endpoint).
  • Postpaid later fits as a credit limit on the billing account (added to the spendable formula) plus invoices built from the ledger; nothing else has to change.

3. Frontend

Server-rendered ASP.NET Core Razor Pages with two layouts (Pages/Shared/_Layout.cshtml for signed-in staff, _AuthLayout.cshtml for sign-in and error pages), the vendored "Aurora" UI kit plus an app stylesheet, and one small vanilla JS file per interactive page. There is no bundler, no npm and no frontend framework. Razor runtime compilation is off, so .cshtml changes need a rebuild. 5. Key flows (low-level)

5.1 Inbound WhatsApp message to AI reply

  1. Meta posts raw JSON to POST /api/integrations/whatsapp/webhook.
  2. MetaWebhookParser splits it into ParsedMetaEvents (customer message, business-app echo, status, template, health, history, app-state, unknown). Interactive/button replies become clean text plus SelectedValue.
  3. MetaWebhookProcessor resolves the clinic per event from channel_integrations (phone_number_id, else WABA id) and dispatches to the handler.
  4. CustomerMessageHandler → LeadService.GetOrCreateByPhoneAsync → conversation get-or-create → MessageService.IngestAsync: idempotent on (clinic, channel, external_message_id), stores the message, opens the 24h window, unread, campaign reply attribution, events, notifications, NewMessage.
  5. If the event is AI-eligible (customer message, conversation mode ai, not a duplicate) the controller calls AiTriggerNotifier → N8n:AiWebhookUrl with {clinicId, conversationId, leadId, messageId, channel, messageType, messageText, selectedValue}. Never throws.
  6. Meta always gets HTTP 200.
  7. n8n AI agent calls /api/ai/* tools, then POST /api/conversations/{id}/messages/send?clinicId= with sender:"ai".
  8. MessageService.SendAiReplyAsync re-reads the mode; if a human took over it returns 409 and nothing is sent. Otherwise WhatsAppChannelSender sends through the Graph API and the message is stored with origin=ai.

5.2 Staff reply, echo and status

  • Staff reply from the Inbox: POST …/messages/send (session) → MessageService.SendAsync → channel sender (throws before persisting if it cannot send; WhatsApp requires an open 24h window) → store origin=dashboard → mode flips to human.
  • Closed window: 409; the Inbox offers send-template with an approved template.
  • Coexistence echo: a reply typed in the WhatsApp Business phone app arrives as a BusinessAppEcho, is stored with origin=whatsapp_business_app, flips the conversation to human, and never triggers AI.
  • Delivery status: MessageStatusHandler updates delivery_status and the matching delivered_at/read_at/failed_at, mirrors campaign recipient status, raises OUTBOUND_MESSAGE_FAILED on failure, broadcasts MessageStatusUpdated.

5.3 Conversation modes

mode ∈ {ai, human, approval}. Switches to human: staff Take Over, a staff message or template, a business-app echo, the AI's handoff_to_human, a campaign template send. Only Return to AI switches back. approval exists in the schema but is never set automatically.

5.4 Telegram

  1. Staff paste a BotFather token on Messaging Integrations → POST /api/channel-integrations/telegram/connect → getMe, then setWebhook to {App:PublicBaseUrl}/api/integrations/telegram/webhook/{channel_integrations.id} with a random secret_token.
  2. Telegram posts an update; the controller checks the row is telegram + connected (else 404) and the secret header (else 403).
  3. TelegramWebhookProcessor → lead by external_lead_id (no phone) → conversation keyed by external_thread_id = chat.id → IngestAsync with external id chatId:messageId, origin=telegram_customer.
  4. Same AI trigger as WhatsApp with channel:"telegram". Outbound goes through TelegramChannelSender → sendMessage. No 24h window; templates are WhatsApp-only.

5.4b WhatsApp through Infobip (MVP provider)

  1. WhatsApp:Provider=infobip makes the Messaging Integrations WhatsApp card ask for a number instead of Facebook sign-in. SculptFlow first registers the number as a sender on its single Infobip account (portal); the clinic then enters it → InfobipWhatsAppIntegrationService.ConnectAsync → Infobip GET /whatsapp/1/senders/{sender}/business-info → row with provider=infobip, provider_sender_id, random webhook_verify_token.
  2. The card's details show {App:PublicBaseUrl}/api/integrations/whatsapp/connections/{channel_integrations.id}/events?token=…; SculptFlow sets it as the sender's inbound forwarding URL in Infobip.
  3. Infobip posts {results:[…]}; the controller checks the row (else 404) and the token (else 403). InfobipWhatsAppWebhookParser classifies each result (has message = inbound, seenAt = read, status = delivery report) into ParsedMetaEvent, and the processor reuses CustomerMessageHandler / MessageStatusHandler, so leads, conversations, the 24h window, campaign attribution, SignalR and notifications are exactly the Meta path. An inbound result addressed to a different sender number is logged as unknown, not filed.
  4. Same normalized AI trigger to n8n, once per conversation per delivery. The AI reply goes back through WhatsAppService → InfobipWhatsAppProvider → POST /whatsapp/1/message/text with our GUID as messageId and notifyUrl = the clinic's webhook URL.
  5. Status mapping: PENDING/ACCEPTED → sent, DELIVERED → delivered, seen report → read, UNDELIVERABLE/EXPIRED/REJECTED → failed (error name/description as failure code/reason).
  6. White-label rule: clinics must never see that WhatsApp runs through Infobip. Errors shown to staff (send failures, connect errors, campaign failure reasons, delivery failure reasons) are provider-neutral, the webhook path is neutral, ChannelIntegrationResponse.Provider/ProviderSenderId are [JsonIgnore], inbound media metadata stores only a mediaId (not Infobip's media URL), and the page's form/handler names are neutral. Details go to the server log only.
  7. Idempotency: inbound dedup on (clinic, channel, external_message_id); a repeated status is a no-op and a late earlier step (delivered after read) only fills its timestamp (MessageService.HandleStatusUpdateAsync, applies to Meta too). Errors after auth return 500 so Infobip retries.

5.5 Booking (AI and dashboard)

  1. get_available_slots → AvailabilityService.GetSlotsAsync builds slots in the clinic's timezone and returns the lead's booking context.
  2. schedule_consultation → AppointmentService.ScheduleAsync: no upcoming appointment → book; one upcoming and ConfirmReplaceExisting → reschedule; otherwise CONFIRMATION_REQUIRED.
  3. Every mutation takes pg_advisory_xact_lock(hashtext(clinicId)), re-runs CheckSlotAsync (excluding the appointment being moved) and the one-upcoming-per-lead guard.
  4. After commit: event row, APPOINTMENT_* notification, AppointmentChanged, and CalendarIntegrationService.TriggerAppointmentSyncAsync.

5.6 Campaigns

  1. Create (/Campaigns/Create): pick an approved template, fill variables, choose audience all_eligible | reactivation_no_consultation | custom (filters JSON or manual selection). Recipients are snapshotted; non-contactable leads are skipped with a reason.
  2. Send: POST /api/campaigns/{id}/send moves to running, queues pending recipients and processes the first batch (20). process-batch continues until complete.
  3. Each recipient: conversation get-or-create → MessageService.SendCampaignTemplateAsync (origin=campaign, links campaign ids) → mode flips to human.
  4. Attribution: status webhooks move recipients through sent → delivered → read; the first inbound reply after sent_at sets replied_at and CAMPAIGN_REPLY; bookings set booked_at/appointment_id.

5.7 Calendar sync (one way, SculptFlow → Google/Outlook)

  1. Connect: /calendar-oauth/{provider}/connect marks the row pending and redirects to consent; /callback exchanges the code, stores access/refresh tokens on calendar_integrations, lists calendars into calendar_integration_calendars.
  2. Staff select a calendar and enable sync.
  3. On every committed appointment change, the service refreshes the token if needed, upserts appointment_calendar_syncs (one row per appointment × integration, new last_request_id, last_operation) and posts CalendarSyncTriggerPayload to N8n:CalendarSyncWebhookUrl (access token, calendar id, operation create/update/cancel, request id, external event id, start/end with offset, clinic timezone).
  4. n8n makes the provider call and posts {clinicId, appointmentId, calendarIntegrationId, requestId, success, externalEventId, errorMessage} to /api/calendar-integrations/sync-callback. A stale requestId is ignored. Failures mark the integration unhealthy.

5.8 Knowledge Base ingestion and search

  • Manual / upload: text (or extracted text, max 5 MB file, 250k chars) → chunk by the clinic's settings (tokens ≈ chars ÷ 4) → embed all chunks first → transaction replaces knowledge_chunks for that document.
  • Website: create source → pending run enqueued → worker crawls breadth-first (robots.txt, SSRF-checked fetch, same-site links, max pages/depth/concurrency from Knowledge:WebScraping) → analyze (canonicals, boilerplate stripping by block hash, SHA-256 of normalized text, duplicates) → apply (unchanged pages skip embedding, changed pages rebuild only their chunks, new pages create source_type='website' documents, missing pages deactivate after confirmed absence).
  • Search: embed the query with the clinic's model, exact cosine scan over the clinic's active documents' chunks, take top-K, drop anything under minimum_similarity. No ANN index on purpose.

5.9 Retrieval benchmark

  1. Generate: the app creates a pending generation row, samples 20 active chunks and posts them with the generationId to N8n:KnowledgeBenchmarkWebhookUrl; returns 202.
  2. n8n's LLM writes one question per chunk and calls back POST /api/knowledge/benchmark/generations/{id}/questions. Every id is validated against the chunks that generation sent; the clinic comes from the generation row. Cancelled generations refuse late callbacks.
  3. Run: a pending run is queued; the worker searches each non-stale case via SearchRankedAsync and records chunk/document ranks, Top-1/3/5, MRR, latency and a settings snapshot.

5.10 Sign up and sign in

  • Register: full name, clinic name, email, password → new clinic (unique slug) + user + membership in one transaction → signed in → /dashboard.
  • Google: /auth/google/start → Google → /auth/google/callback: existing linked login or verified matching email signs in; a new email goes to /Account/CompleteGoogleSignup to collect the clinic name. Errors return to Login with externalError=cancelled|failed.

5.11 Billing an outbound WhatsApp template (usage)

  1. MessageService (Inbox template, campaign recipient, or a billed free-form message) checks the subscription (EnsureCanSendMessages; expired/cancelled/no plan → 422) and generates the message id it will save.
  2. WhatsAppBillingPolicy describes the message: template category → whatsapp_{category}_message (utility inside an open 24h window and free-form replies are free by default), quantity 1, destination country from the lead's number, provider = the active WhatsApp:Provider, settle on delivery.
  3. ProviderBillingService resolves the clinic's WhatsApp account: who pays the provider (account override, else the default — platform_funded for WhatsApp) and whether SculptFlow charges usage.
  4. SculptFlow doesn't charge (customer pays Meta directly, external provider, no fee): BillingService.Reserve only records the usage as not_charged, with Meta's cost if a rate knows it. No rate is required, nothing is held, the send goes ahead even with an empty wallet, and the outcome steps below only update provider_outcome.
  5. SculptFlow charges: BillingService.Reserve (own transaction, clinic account locked) rates it (clinic card → plan card → default, rate effective now, most specific country/operator/provider/arrangement; a customer-paid account only matches a fee rate for its own arrangement), refuses if no rate or spendable < price (recorded as a failed usage row; the send is refused with 422 before the provider is called), else holds it and inserts the usage record keyed whatsapp:message:{messageId}.
  6. The provider call runs. If it throws, the hold is released (send_failed) and the error goes back as before.
  7. The message row is saved with the same id. Later, the provider's status callback reaches MessageService.HandleStatusUpdateAsync (Meta or Infobip, same path) → MessageBillingService: delivered/read → settle (release the hold, charge included credit first, then wallet, one ledger row per balance), failed → release. Repeated or out-of-order callbacks are no-ops; settle-after-release is refused and logged.
  8. If no outcome arrives within Billing:ReservationTimeoutHours, the maintenance worker settles it when the message row shows it was delivered (callback processed but billing failed) and releases it otherwise.

5.12 Subscription start, renewal and expiry

  1. Start / change plan (admin API, or the signup plan): wallet must cover the price while keeping existing holds covered (unless the first period is waived); old included credit expires, the plan's credit is granted, the price is charged (a 0 charge row for free/trial periods), the period runs from now. Same idempotency key → no second charge.
  2. Renewal (worker, when current_period_end has passed): same steps for the next contiguous period. If the wallet can't pay: past_due, the ended period's credit expires, the plan keeps working for Billing:GracePeriodDays; every worker run retries, so a top-up renews it (from the old period end).
  3. Expiry: grace over without payment → expired. Cancel: now, or at period end instead of renewing → cancelled. Expired/cancelled clinics can sign in and see everything, but can't send, run campaigns, use the AI or connect channels until a plan is started again.

8. Database

8.1 Conventions

  • One Postgres schema per area (since 2026-10-07): core (clinics, procedures), identity (ASP.NET Identity, clinic_users), crm (leads, conversations, messages), scheduling (appointments, procedure bookings, availability, calendar sync), channels (channel integrations, WhatsApp templates and health, TikTok), marketing (campaigns), knowledge (knowledge base, scraping, benchmarks), activity (events, notifications), billing, config; the admin portal's own tables are in admin. public keeps only set_updated_at() and extensions. SQL always schema-qualifies table names and every ToTable names its schema. The top of schema.sql creates the schemas and moves any table still in public (databases created before the split) with alter table … set schema, which keeps data, indexes, constraints, triggers and foreign keys; on a current database it does nothing. Supabase's Data API only exposes public, so no app table is reachable through it.
  • Database/schema.sql is the source of truth: idempotent, append-only blocks (create … if not exists, add column if not exists, guarded do $$ constraint blocks). New changes are appended at the end, never edited in place. ApplicationDbContext is updated by hand to match.
  • Keys: uuid with gen_random_uuid(), except Identity (text ids) and knowledge_retrieval_benchmark_generations.id (app-assigned).
  • created_at/updated_at on most tables; set_updated_at() trigger maintains updated_at.
  • All instants are timestamptz; a guard block at the end converts any stray timestamp column. Only availability time/date columns are zone-less (clinic-local).
  • Status columns are varchar with CHECK constraints, except deliberately free-text provider vocabularies (template status/category, health fields, campaign_type, leads.source, knowledge_documents.category).
  • Tenant FK clinic_id … on delete cascade everywhere. Tokens (access_token, refresh_token) are plain text today.

9. Configuration

Names only. Non-secret defaults live in appsettings.json; secrets via user-secrets or Render env vars (__ for :).

Settings in the database (config.settings, read through IConfigManager). Tunable values (limits, defaults, thresholds) are read with IConfigManager.GetInt/GetDecimal/GetBool/GetString(section, key) (Business/Managers/ConfigManager, singleton): the value stored in config.settings for that section and key when there is one, otherwise the constant default declared in Common/Statics/ConfigDefaults.
