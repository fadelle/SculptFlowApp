# Bugs found while writing unit tests

## Status (2026-10-08)

**Fixed, with the formerly skipped test now running:** BUG-01, 02, 06, 08, 09, 10, 11, 12, 13, 14, 15.
**Withdrawn:** BUG-03. The code comments show it is intended: AI appointment ids go stale, so with one upcoming appointment the backend picks it itself (the test now pins that).
**Also fixed (2026-10-09):** NOTE-01 (malformed campaign filters now rejected at creation), the logging and missing `[ApiErrors]` parts of NOTE-05 (the TikTok webhook is still anonymous).
**Still open:** BUG-05 (campaign "Booked" stat is a feature gap), BUG-07 (needs a product decision, test still skipped), and every NOTE row.
Behaviour changes worth knowing: the Meta webhook now answers 401 unless `Meta:AppSecret` is configured and the delivery is signed; `IMetaWebhookProcessor` gained `ProcessAllAsync`; the embedding error message is now "The embedding service is unavailable (HTTP nnn)".

The table below is the original report (rows kept for history).

Found while writing the Stage 1 unit tests (business layer). Production code was not changed. Each BUG with a test in the last column has a skipped test (`[Fact(Skip = "BUG-nn ...")]`) that asserts the correct behaviour: fix the code, then delete the `Skip` and it should pass. NOTE rows are risks or things to confirm, not confirmed defects. BUG-04 was withdrawn after checking the real provider clients (they already swallow revoke failures).

| Id | Severity | Where | What | Test |
|---|---|---|---|---|
| BUG-01 | Low | `Common/Helpers/ConfigValues.cs` `Validate`/`ToDecimal` | Decimal settings parse with `NumberStyles.Number`, which allows thousands separators: "1,5" validates OK and is stored/read as 15 (an admin typing a European decimal silently gets 10x the value). Fix: use `NumberStyles.AllowDecimalPoint \| AllowLeadingSign`. | `SimpleHelperTests.Decimal_with_comma_is_rejected` |
| BUG-02 | Low | `Common/Helpers/StatusBadgeHelper.cs` `TemplateStatusLabel` | An upper-case status such as Meta's "APPROVED" is shown as "APPROVED" (only lower-case input is capitalised), and `Capitalize` does not lower-case the rest. Fix: `Capitalize(status.ToLowerInvariant())`. | `SimpleHelperTests.TemplateStatus_label_is_case_insensitive` |
| BUG-03 | Medium | `Business/Services/Appointments/AppointmentService.cs` `CancelConsultationAsync` / `ScheduleAsync` | With exactly one upcoming appointment, an explicit `appointmentId` that is NOT that appointment is silently ignored (`existing.Count == 1 ? null : id`, `target = existing[0]`), so the AI tool cancels or moves the patient's only appointment even though it named a different one. Fix: when an id is given, always check it is in `existing` (INVALID_REQUEST otherwise). | `AppointmentServiceTests.CancelConsultation_with_a_foreign_id_and_one_upcoming_is_rejected` |
| BUG-05 | Low | `Business/Services/Campaigns/CampaignService.cs` `ComputeStatsCore` (+ `MessageService` appointment flow) | The "Booked" campaign stat counts recipients with `Status == Booked` or `BookedAt`, but nothing in the app ever sets either (nothing in the code writes either), so the Booked column and the admin portal's booked count are always 0. Either attribute bookings to the campaign (e.g. when `AppointmentService` books a lead who replied to a campaign recently) or hide the column. | none (feature gap; no unit-level assertion possible) |
| NOTE-01 | Medium (design risk) | `Entities/Dtos/Campaigns/CampaignAudienceFilters.cs` `Parse` | Malformed audience-filter JSON silently becomes "no filters", so a campaign with a typo in its filters targets the whole eligible audience instead of failing. Consider throwing `ArgumentException` when the JSON can't be parsed, at least at campaign creation. | `CampaignAudienceServiceTests.Filters_parse_leniently` pins the current behaviour |
| BUG-06 | Medium | `Business/Services/Procedures/ProcedureBookingService.cs` `CreateAsync` / `UpdateAsync` | `CreateAsync` only checks the procedure; the `LeadId` (and `AppointmentId`) from the request are never checked against the clinic, and `UpdateAsync` loads the lead with the unscoped `GetByIdAsync`. A staff user who knows another clinic's lead GUID can attach a booking to it and, by completing the booking, flip that lead's status. Fix: `_leads.ExistsAsync(clinicId, leadId)` (and the same for the appointment) before creating, and load the lead with the clinic-scoped `GetAsync`. | `ProcedureBookingServiceTests.Create_rejects_a_lead_from_another_clinic` |
| BUG-07 | Low (needs product confirmation) | `ProcedureBookingService.UpdateAsync` | The lead becomes `surgery_booked` and `procedure_booked` is logged only when the booking is set to `completed`, never when it is set to `booked` (or `deposit_paid`). Reads like the trigger should be `Booked`. | `ProcedureBookingServiceTests.Marking_a_booking_as_booked_moves_the_lead_to_surgery_booked` |
| BUG-08 | Medium | `Business/Engines/WhatsApp/MetaWebhookProcessor.cs` `ProcessAsync` | A Meta webhook POST can carry several messages (even from different customers). The processor returns only the first AI-eligible response (`results.FirstOrDefault(r => r.ShouldRunAi) ?? results[^1]`), so the controller triggers the AI for one conversation and the others get no AI reply. The Infobip processor already returns every result and triggers once per conversation. Fix: return the list and trigger per conversation. | `MetaWebhookProcessorTests.Every_ai_eligible_message_in_a_batch_triggers_the_ai` |
| NOTE-02 | Low (needs checking against Meta's payload) | `MetaWebhookParser.ParseHealthEvent` + `WhatsAppHealthService.RecomputeHealth` | The parser stores `current_limit` (a messaging tier such as `TIER_1K`) in `HealthQualityRating`, and the health service then compares `PhoneQualityRating` with "red"/"yellow". If Meta's `phone_number_quality_update` carries no separate colour rating, the red/yellow health states can never be reached from a webhook; only `event` values like FLAGGED trigger a warning. | none |
| BUG-09 | Low-Medium | `Business/HttpClients/OpenAi/OpenAiEmbeddingService.cs` `EmbedOneRequestAsync` | A non-2xx embeddings response is put (first 300 chars) into an `InvalidOperationException`; `[ApiErrors]` returns `InvalidOperationException` messages to the browser (HTTP 422). OpenAI's 401 body includes a masked copy of the platform API key, so a clinic user saving a Knowledge Base document during a key problem would see it. Fix: log the body, throw a generic "The embedding service is unavailable (HTTP 401)". | `OpenAiEmbeddingServiceTests.Provider_error_bodies_never_reach_the_caller` |
| BUG-10 | Low | `Business/Managers/ConfigManager.cs` `Apply` | The snapshot is built with `ToDictionary` on lower-cased (section, key). Two stored rows that differ only in letter case throw `ArgumentException`; `RefreshAsync` catches it and logs, so every later refresh silently fails and the settings stay stale. Fix: last-write-wins (`GroupBy(...).Select(g => g.OrderBy(UpdatedAt).Last())`) or a case-insensitive unique index. | `ConfigManagerTests.Rows_that_differ_only_by_case_do_not_break_the_snapshot` |
| BUG-11 | Low | `Common/Converters/LenientNullableGuidConverter.cs`, `LenientNullableDateTimeOffsetConverter.cs` | A bare JSON number for an id/date (for example `appointmentId: 5` sent by the AI tool) makes `reader.GetString()` throw `InvalidOperationException`, which MVC does not turn into a 400, so the endpoint answers 500. Fix: check `reader.TokenType` and throw `JsonException`. | `LenientConverterTests.A_number_where_an_id_is_expected_is_a_json_error_not_a_crash` |
| BUG-12 | Low | `Controllers/Filters/RequireIngestKeyAttribute.cs` | The n8n ingest key is compared with `!=`, not a constant-time comparison like `RequirePlatformAdminKey` uses, so it is theoretically guessable by response timing. Fix: `CryptographicOperations.FixedTimeEquals`. | `AuthorizationFilterTests.Ingest_key_comparison_is_constant_time` |
| BUG-13 | **High** | `Controllers/Integrations/WhatsAppWebhookController.cs` `Receive` | The Meta webhook POST never verifies `X-Hub-Signature-256` (the controller's own comment says so). Fix: HMAC-SHA256 of the raw body keyed with `Meta:AppSecret`, constant-time compare, reject with 401/403 before processing. The Infobip and Telegram webhooks do check a per-connection secret. | `WebhookControllerTests.Forged_posts_without_a_valid_signature_are_rejected` |
